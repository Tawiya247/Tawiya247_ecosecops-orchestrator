Le guide officiel du Hackathon IBM Bob 2.0 (hébergé sur Lablab.ai) définit les règles, les méthodologies de travail recommandées et les critères d'évaluation pour ce challenge de 48 heures.1. Focus sur la section : « A note on data sets before you begin »Cette section pose le cadre sur l'utilisation des jeux de données (datasets) et la sécurité avant de démarrer le code :Sécurité des identifiants et clés API : C'est le point de vigilance majeur. IBM effectue une surveillance automatique des dépôts GitHub. Si des identifiants ou clés API IBM Cloud sont détectés dans votre code, votre compte peut être immédiatement suspendu.Utilisez le template GitHub fourni par IBM.Veillez à utiliser correctement les fichiers .gitignore et .bobignore pour bloquer la publication accidentelle de secrets.Choix et conformité des données : Si vous utilisez des jeux de données externes (pour alimenter votre application ou enrichir les modèles), assurez-vous qu'ils sont libres de droits (open data ou sous licence permissive), anonymisés et exempts de données confidentielles ou personnelles.Intégration dans le contexte : La gestion des données doit servir à nourrir les fonctionnalités de votre projet (via IBM Bob ou les services optionnels comme IBM watsonx.ai, Natural Language Understanding ou Cloudant) sans saturer inutilement la mémoire de votre agent IA.2. Qu'est-ce qu'IBM Bob 2.0 dans ce hackathon ?IBM Bob 2.0 n'est pas un simple autocompléteur de code, mais un partenaire IA de développement. Il comprend le contexte global du projet, l'architecture et les intentions :Il aide à la planification, la génération de code, la création de documentation, l'écriture de tests et la création de subagents.Son utilisation est obligatoire dans votre solution et sera directement évaluée par le jury.3. Bonnes pratiques méthodologiques avec IBM BobLe guide met fortement l'accent sur la gestion de la fenêtre de contexte (context window) de l'agent :Principe « Une tâche, une session » : Ne mélangez pas l'exploration, l'architecture et l'implémentation dans la même discussion. Ouvrez une nouvelle session pour chaque tâche distincte pour éviter de polluer le contexte de Bob (context poisoning).Conservez le savoir dans des fichiers, pas dans le chat : Les plans, règles et décisions d'architecture doivent être écrits dans des fichiers Markdown (par exemple agents.md ou des fichiers de règles).Méthode Rollback vs Argumentation : Si Bob dérive ou produit un mauvais résultat, il est recommandé de faire un retour en arrière (rollback) vers le dernier bon message et de reformuler votre consigne au lieu de débattre avec l'IA dans la discussion.Le cycle recommandé : Explore $\rightarrow$ Plan $\rightarrow$ Implement $\rightarrow$ Verify.4. Livrables obligatoires pour la soumissionÀ la fin des 48h, vous devrez fournir sur la plateforme :Un dépôt GitHub public contenant votre code source, sécurisé (sans clés API) et structuré.Captures d'écran des résumés de session IBM Bob (Task Session Summary Screenshots) montrant la preuve de l'utilisation de Bob par chaque membre de l'équipe.IBM Bob Usage Statement (max. 500 mots) : Une explication détaillée expliquant où et comment Bob (et éventuellement watsonx) a contribué à la construction du projet.Description du projet (max. 500 mots) : Problématique ciblée, utilisateurs visés, originalité et valeur de la solution.Vidéo de démonstration (3 minutes max) :Présentation rapide du problème.Au moins 90 secondes de démo en direct montrant l'application en fonctionnement.Explication orale claire du rôle joué par IBM Bob.5. Critères d'évaluation des jugesApplication de la technologie (Application of Technology) : Intégration concrète, pertinente et poussée d'IBM Bob 2.0.Valeur métier (Business Value) : Impact réel du problème traité et pertinence de la réponse apportée.Présentation : Qualité de la démo vidéo et clarté des explications.
